## Goal and authority

Deliver the 17 accepted 0.4.0 issues with a finite production scenario set and approval-gated release evidence. Source: assessment.md, predecessor reflection, evidence/issue-inventory.json, and the operator's 2026-10-24 batched response recorded in operator-gates.md.

History rewrite and actual publication still require separate scoped approval. Coding may finish while those external steps remain pending; release certification may not silently pass them.

## Approach and scope

Use existing contracts and backends; change the two mailbox contracts once, then apply those definitions across PG/redb and runtime callers. Keep scheduler edits with one owner. Build one final integration packet after all production changes rather than running per-edit suites. No new queue technology or runtime is proposed, so optional Analyze is skipped: no build-versus-adopt investigation is needed for the core fixes. Official docs/version verification for release tooling remains an explicit implementation prerequisite.

Compared with “ship every milestone enhancement”, this bounded assurance scope avoids adding durable scheduling features while repairing correctness and verification gaps. Compared with “code fixes only”, it preserves the separately accepted release-control work. These are driver tradeoffs; no unasked optional item enters totals.
