## Real workloads and comparability

Baseline production revision is exactly
`92da0d3d28f7896ddc67062fa49ba40ea48d74a3` (0.3.0). The staging command
requires a clean scratch checkout and adds only identical `pg_backend.rs`
bytes plus the approved Cargo bench stanza. Build rejects other baseline
changes. Candidate must be clean at its actual full frozen SHA. No candidate
SHA is invented in this authored handoff. Source identity, exact manifest
injection, manifest/lock/harness hashes, Cargo JSON artifact, binary hash,
features, profile, actual rustc/Cargo and raw build logs bind both arms.
The same harness compares outcomes only with `Stored`, supporting baseline's
unit Duplicate and candidate's Duplicate-with-status without a shim.

Each process connects to its own new Docker PG database and runs its binary's
real queue/mailbox migrations. No shared upgraded store or relabeled schema
is used. Cases are `queue` (enqueue/lease/ack), `mailbox_unique`
(deliver/peek/consume), `mailbox_duplicate` (one shared preseeded address/key
fence), and `durable` (actual DurableResourcePool submit/executor/result
consumption). The queue case checks all leased IDs exactly once, even when
clients lease one another's submissions. Durable leases/accounting drain
after the timed phase. No fake backend, in-memory replacement or task-count
timing is the production measurement path.

Frozen workload: four Tokio worker threads, clients1/8, SQLx maximum10,
1,024 measured operations after 128 warm-up operations, 256-byte payload,
Normal priority, one-unit CPU cost, 16 pool units, 30s lease and 1ms polling.
IDs are deterministic sequential inputs. Each timed latency includes its
client cycle, checks, storage calls and polling, not pure database-server
latency. Fresh mailbox and durable clients use independent addresses;
duplicate clients contend on one address/caller-key fence. This measures
real concurrent PG/pool paths, not an isolated bare semaphore/dispatcher lock.

With five pairs, the normal matrix is80 processes: four cases × two client
counts × five pairs × two arms. Each case/client cell has five baseline and
five candidate samples. Pair order alternates; every arm gets a fresh
container. The separate slow control is10 processes: hot-key case, clients8,
five pairs. Candidate adds a declared100ms delay per measured operation;
baseline delay is0. The base operation sequence stays fixed, but that
perturbation is explicit and cannot enter a normal performance report.

## Final-boundary command protocol (proposed, not run)

OA-18 supplies actual `OA17_BASELINE_ROOT`, `OA17_CANDIDATE_ROOT`,
`OA17_CANDIDATE_SHA`, `OA17_EVIDENCE_ROOT` and `OA17_QUIET_ATTESTATION`.
The fresh evidence directory and its build receipts/logs must be outside
both source trees, avoiding new untracked files in the clean candidate or
extra files in the constrained baseline. Create its parent first. Run the
following from the frozen candidate root. Stage/build are preparation before
the quiet interval; one Cargo writer, no ambient model/negative Rust flags.

```bash
python3 benches/pg_measure.py stage-baseline --root "$OA17_BASELINE_ROOT" --candidate-root "$OA17_CANDIDATE_ROOT" --out "$OA17_EVIDENCE_ROOT/staging.json"
python3 benches/pg_measure.py build --arm baseline --root "$OA17_BASELINE_ROOT" --revision 92da0d3d28f7896ddc67062fa49ba40ea48d74a3 --out "$OA17_EVIDENCE_ROOT/baseline-build.json"
python3 benches/pg_measure.py build --arm candidate --root "$OA17_CANDIDATE_ROOT" --revision "$OA17_CANDIDATE_SHA" --out "$OA17_EVIDENCE_ROOT/candidate-build.json"
```

Each build records this actual Cargo argv and uses its source root's isolated
`target/oa17-build`:

```bash
cargo bench -p prometheus_parking_lot --locked --no-default-features --features tokio-runtime,postgres --bench pg_backend --no-run --message-format=json
```

Stop active agents/builds/other benchmarks before collection and keep them
stopped throughout. The attestation example is false/empty by design; the
operator supplies a truthful copy naming the machine and operator. There is
no automatic host tuning, process killing, cache clearing, image build/pull
or tool installation. Known process-name guards and before/after snapshots
support the attestation but cannot prove complete inactivity between
snapshots or detect every wrapped/background agent. That limitation cannot
be concealed by setting the flags true.

```bash
python3 benches/pg_measure.py measure --baseline-receipt "$OA17_EVIDENCE_ROOT/baseline-build.json" --candidate-receipt "$OA17_EVIDENCE_ROOT/candidate-build.json" --image parking-lot-pg:18 --quiet-attestation "$OA17_QUIET_ATTESTATION" --samples 5 --max-wall-seconds 7200 --out "$OA17_EVIDENCE_ROOT/normal"
python3 benches/pg_measure.py report --capture "$OA17_EVIDENCE_ROOT/normal" --out "$OA17_EVIDENCE_ROOT/report.json"
python3 benches/pg_measure.py measure --baseline-receipt "$OA17_EVIDENCE_ROOT/baseline-build.json" --candidate-receipt "$OA17_EVIDENCE_ROOT/candidate-build.json" --image parking-lot-pg:18 --quiet-attestation "$OA17_QUIET_ATTESTATION" --samples 5 --max-wall-seconds 7200 --slow-control --out "$OA17_EVIDENCE_ROOT/slow-control"
python3 benches/pg_measure.py report --capture "$OA17_EVIDENCE_ROOT/slow-control" --allow-slow-control --out "$OA17_EVIDENCE_ROOT/slow-control-report.json"
python3 benches/pg_measure_test.py -v
```

The two-hour per-capture envelope, 2,400s child watchdog and 120s external
command watchdog are resource limits, not performance thresholds. One
fresh database/container is owned at a time. A normal process has at most
eight workload clients, four Tokio worker threads and the recorded ten
SQLx connection limit. No benchmark elapsed time or throughput is asserted
here. A different PG major requires another isolated capture/report with its
prebuilt image; different machines/images are never merged into one pair set.

The actual `measure --slow-control` real-PG run is separately mandatory.
Its report with `--allow-slow-control` must validate ten raw samples and
observe a throughput/latency regression. Otherwise it fails
`OA-17:slow-classifier`; RSS-only movement cannot satisfy that oracle.
It emits `MEASURED_CONTROL_ONLY`, never normal performance evidence. A normal
validated report is `MEASURED_REPORT_ONLY`, not a release verdict. Synthetic
test success cannot replace normal80 or slowed10 collection. Compilation,
environment failure, timeout, missing discovery or unrelated exception is
not an expected control finding. Retain exact exits and named diagnostics.

## Metrics, raw artifacts and uncomfortable limits

Reports expose each process's throughput, nearest-rank p50/p95/p99 latency,
and peak RSS, with raw sample arrays, paired ratios and deterministic paired
95% bootstrap cost-ratio intervals (10,000 resamples, seed0x5eed). Throughput
ratios are inverted to express cost. A cost interval wholly above1 is an
observed regression, wholly below1 is improvement, and overlap is
inconclusive. No numerical release threshold or general regression budget
is introduced; the existing Criterion +25% warning policy is separate.
Every observed regression is reported explicitly for the operator. Five
pairs and bootstrap intervals do not establish universal performance or
eliminate frequency, filesystem/cache and background-load effects.

Peak RSS is exact per client/pool process from wait4, including process
startup, migrations, warm-up, measured work and shutdown. Linux native KiB
and macOS native bytes are retained and normalized. PostgreSQL server,
Docker daemon/VM and Python runner RSS are excluded. The driver explicitly
approved this client-memory interpretation of issue71/OA-17; Docker VM
CPU/memory capacity and limits are comparability identity, not cgroup memory
or database-process RSS. There is no broader server-memory claim.

Keep staging/build receipts, unmodified capture manifests and all referenced
raw sample JSON, per-operation latency arrays, stdout/stderr, build logs,
process snapshots, native RSS fields, exact argv/exits and timestamps. Keep
the full CPU/OS/thread/memory/Python identity, actual rustc/Cargo/features/
profile, Docker client/server/VM configuration, immutable image ID and any
repository digests, PG version and container resource limits. Disposable
credentials are generated per container and redacted from client logs.
Freeze the manifest digest with the final full candidate SHA, adopted
contract digest, fixture/harness/tool hashes and this scenario's complete
normal/control manifest in OA-18 evidence. Missing raw data, source/binary
drift, machine/image/workload drift and failed processes cannot be hidden
by summarizing aggregate counts.
