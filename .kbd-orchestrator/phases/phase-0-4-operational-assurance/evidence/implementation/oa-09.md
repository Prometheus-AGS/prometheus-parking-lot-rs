## Named failure and implementation delta

Issue #82 concerns an impossible head already stored in a TaskQueue backend
before ResourcePool owns it. Such work did not pass the current dispatcher's
submission check. Previously the head could remain parked forever, even when
all running work had released its units, blocking valid followers. Separately,
the pre-filled tasks were absent from the pool ledger, so their completion or
expiry could decrement an accepted count that never included them.

The tech lead approved the exact shared interface before implementation:
`Dispatched<T>::rejected: Vec<(T, SchedulerError)>`, together with its default,
emptiness, literals, merge and terminal-reporting obligations; and the
method-level `Q: TaskQueue<P>` bound on `ResourcePool::new` needed to seed
accounting from `queue.len()`. No new parallel trait or error variant was added.

Task1 changed seven owned files:

- `crates/parking-lot-core/src/dispatch/dispatcher.rs`: drain calls existing
  `check_capacity` on each observed head before expiry or permit acquisition;
  impossible heads leave once with their error. Rejected-only batches are
  nonempty and merges retain rejected entries. The `oa-09` negative control
  suppresses this head check only, leaving direct-submission checks enabled.
- `crates/parking-lot-core/src/dispatch/parked.rs`: updated the adapter's
  removal obligation comment; no adapter trait or storage change in OA-09.
- `crates/parking-lot-core/tests/backend_admission_test.rs`: four new
  integration fixtures over the real Dispatcher/TaskQueueAdapter/InMemoryQueue.
- `crates/parking-lot-runtime-tokio/src/resource_pool.rs`: initial queue depth
  enters the ledger at construction. First release-hook installation drains
  stored work after builder configuration, and `shutdown_with` also initiates
  that observation if no submission occurred. Rejected entries receive their
  terminal handling outside the dispatch lock.
- `crates/parking-lot-runtime-tokio/src/worker_pool/native.rs`: rejected entries

## First observation, outcomes and accounting

Construction transfers the backend's reported existing depth into the pool's
accepted count; it does not spawn work. Builder methods can still configure
the pool's name, limits, hooks and clock. The first valid submission reaching
release-hook installation or `shutdown_with` then drains the pre-filled queue.
Other draining operations can also observe a head. This initial observation
allows a new submission to proceed even when impossible stored heads had
filled the queue to its depth bound.

The drain checks the absolute configured capacity, not the currently free
capacity. A total-over-limit or kind-over-limit head is removed once, without
a permit or executor call, and its `CapacityExceeded` error identifies the
dimension, requested units and configured limit. If an impossible head is also
expired, capacity rejection takes precedence. A valid head that cannot fit
because another task holds the needed total or kind units remains parked and
uses the incumbent skip-ahead/starvation policy.

ResourcePool emits `LifecycleEvent::Rejected` with
`RejectionReason::CapacityExceeded { kind }` and attempts one configured mailbox
delivery of `TaskStatus::Dropped(error.to_string())`, with no result payload.
It increments `failed_tasks`, counts a finished ledger outcome and settles the
accepted task. It invokes no asynchronous cancellation sink and supplies no
persistent dead-letter store. Directly pre-filled tasks get no fabricated
`Submitted`/`Queued` event from this pool. An ordinary later submission still
uses its normal lifecycle/admission path.

`ShutdownReport::completed` includes finished failures and expiries during
that shutdown's interval. Thus initial rejection before shutdown starts is
outside the report, while rejection/expiry/completion first observed by
shutdown contributes to `completed`. Each pre-filled task enters accounting
once, so normal completion, head expiry and rejection can settle it without
underflow. The initial count relies on a truthful backend `len`; independently
adding entries after queue ownership transfers is outside this accounting.

## Stored-ticket FIFO and scope limit

Valid stored entries retain their tickets and backend policy. The fixtures
check FIFO among pre-filled entries, including explicit nontrivial stored
sequences whose ordering differs from id order. They also check a new
submission behind unsequenced stored entries. Temporary total pressure and
temporary per-kind pressure must not become rejection.

The uncomfortable limit is that the dispatcher still begins its local
submission counter at zero. Importing an arbitrary older sequence epoch with
large sequence numbers and then making new submissions can put new tickets
ahead of older parked tickets under the incumbent ordering. OA-09 does not
recover a cross-epoch global sequence counter. The driver explicitly retained
the incumbent stored-ticket policy for this scope; no claim of FIFO across
arbitrary imported epochs plus new submissions is made.

Mailbox errors, callback panics, blocking collaborators and bounded hook
delivery retain incumbent limits. In particular, one mailbox delivery attempt
does not prove storage if the backend returns an error or panics. These
fixtures use functioning collaborators and do not certify arbitrary callback
failure recovery. The #57 explicit-prune metadata/event gap is left for OA-10;
the pre-filled expiry fixture uses the existing head-expiry path.

## Static synchronization reasoning

No atomic operation, ordering, UnsafeCell path or semaphore algorithm was
added. The new capacity check reads configured absolute limits. Head check,
pop, rejection-list insertion and continued drain all run under the existing
dispatch mutex; returning `Dispatched` transfers full item/error ownership
outside that lock before callbacks. Rejection takes no permit. A valid grant
still claims every dimension through `UnitSemaphore::try_acquire_vector`, so
this path does not provide a way around total/kind admission.

The existing mutex unlock-to-next-lock edge orders queue changes with later
submissions/completions. The finished tally is sequenced before the ledger's
`SeqCst` settlement decrement, which is a release RMW; a shutdown `SeqCst`
load observing settlement acquires preceding effects. Existing `Notify`
registration and `watching`/counter ordering retain the no-lost-wakeup
handshake. The rejection settlement guard encloses callbacks; it does not add
a new lock or await. These are static arguments using unchanged mechanisms,
not an executed model/Miri/property-test result.
