## Named failure and implementation delta

Issue #57 identifies task loss at the reporting boundary: explicit pruning
previously returned only a count, discarding the identity and payload of each
removed task. ResourcePool could decrement aggregate accounting but could
not emit an individual `Expired` terminal event or deliver that task's
mailbox result. A single batch audit entry did not identify those outcomes.

The tech lead supplied the mandatory shared contract before scheduler edits:

```rust
fn prune_expired(&mut self, now_ms: u128)
    -> Result<Vec<ScheduledTask<P>>, SchedulerError>;
```

The returned tasks retain all original metadata and payload, exactly once,
with no `P: Clone` requirement. Expiry is strict `now_ms > deadline_ms`;
equality and no deadline remain live. Survivors keep their ordering metadata.
Returned-item ordering is unspecified. On `Err`, a conforming backend removes
nothing. The shared package includes the in-memory implementation and a
synchronous TaskQueue conformance case; it is a tech-lead-owned package,
not a contract independently invented by this worker.

Task1 changed six scheduler-owned paths:

## Per-task lifecycle, accounting and callbacks

For each explicitly removed task, ResourcePool uses its existing head-expiry
handler outside the dispatcher lock. With functioning collaborators, that
handler emits one `LifecycleEvent::Expired`, increments `failed_tasks`, counts
a finished ledger outcome, settles the accepted task, attempts a configured
mailbox delivery of `TaskStatus::Expired` with no result payload, and records
an individual expiry audit with the original task id and mailbox tenant.
It does not execute the payload or call the asynchronous cancellation sink.
There is no second aggregate decrement. A repeated prune cannot report or
settle an item already removed. Pruned tasks are parked and hold no permit;
the operation leaves active running permits unchanged. The subsequent drain
can admit live work that an expired head had blocked.

The public ResourcePool return remains the number explicitly removed by
pruning, not a replacement metadata API. Dispatcher consumers still receive
the full terminal-reporting obligation through `Dispatched.expired`.
`ShutdownReport::completed` includes finished failures/expiries occurring in
its report interval. Expiries settled before shutdown begins are outside
that interval, so the main fixture expects its three subsequent live
completions there, while cumulative counters include both prior expiries.

The uncomfortable callback limit is unchanged: the incumbent expiry handler
settles before mailbox/audit callbacks. Ledger settlement and a shutdown
report therefore do not acknowledge successful result storage. Mailbox
delivery errors are logged without a new retry; callback panics or blocking
can interrupt or delay the surrounding reporting path. This change does not
claim recovery under arbitrary callback failure, process abort or storage
failure. Hook delivery still has its bounded queue and dropped-event counter.
The production fixture uses returning collaborators, checks no hook drops,
and asserts one observable result/audit/terminal sequence per removed task.

## Error and synchronization semantics

The backend-first adapter order matters: pruning the front first and then
receiving a backend error would lose removed front tasks without a returned
reporting obligation. The adapter now calls the mandatory fallible backend
operation first. On backend `Err`, it returns before front mutation. Once
that succeeds, concrete `PriorityQueue` front pruning is infallible and the
vectors are combined. The failure fixture injects one legal backend error,
observes the front and backend still queued, then confirms the retry returns
both expired tasks exactly once. A backend violating the mandatory
error-leaves-tasks-queued contract is not repaired by this adapter.

No atomic operation, ordering, UnsafeCell path, lock type or semaphore
algorithm changed. Queue removal and admission remain ordered by the
dispatch mutex unlock-to-next-lock edge. Metadata and payload ownership move
into the returned vectors; callers emit no terminal callback under that
mutex. Per-task finished tally updates precede the existing `SeqCst`
settlement decrement, a release RMW; a shutdown acquiring observation of
settlement sees those preceding effects. The ledger's existing
`watching`/counter/Notify handshake still governs wakeups. These are static
arguments about unchanged synchronization, not executed model/Miri/property
evidence.

## Migration, candidate evidence and disposition

Custom TaskQueue implementations must return the full removed tasks instead
of a count, with no removed task lost on success or error. Custom ParkedQueue
implementations analogously return `Vec<T>`. Use the returned ownership to
report terminal results outside dispatcher locks. ResourcePool callers keep
their count return. The shared conformance helper exercises real TaskQueue
implementations; the public patch supplies this migration to API/changelog
readers and removes the obsolete #57 pruning exception.
