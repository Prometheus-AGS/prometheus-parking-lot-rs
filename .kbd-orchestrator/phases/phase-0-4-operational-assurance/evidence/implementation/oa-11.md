## Named failures and implementation delta

The admission failure is a submission and shutdown each missing the other's
state transition: submission accepts work and sees shutdown false while
shutdown sees zero accepted work. The kind-release failure is two concurrent
permit returns losing a kind-counter subtraction when the critical section
is split. Neither is represented by a mock-only parallel implementation.

## Production transitions and ordering argument

ResourcePool's submit path calls `ledger.accept()` before loading its
shutdown flag. Shutdown stores that flag before the shutdown wait predicate
loads `in_flight`. The ledger model preserves those orders. Both normal
ledger operations and both flag operations are SeqCst. Their single total
order excludes the cycle in which both loads see the initial values. This
is an order-cycle exclusion, not a synchronizes-with edge between unrelated
atomic objects. The model retains accepted work until both thread snapshots
are recorded; joining afterward cannot conceal an earlier missed snapshot.
A refused submission settles its acceptance immediately, as production does.

The `oa-11-ledger-order` cfg is effective only with `parking_lot_loom` in
the actual ledger implementation: accept becomes AcqRel and in-flight
observation becomes Acquire. The fixture flag becomes Release/Acquire.
Those operations on different atomic objects do not require either load
to observe the other thread's write. The intended failure is the named
both-missed-work assertion. Settlement stays SeqCst, leaving its publication
companion as a positive control.

The settlement model calls actual `finish(1)` before `settle(1)`. The
Relaxed finished increment precedes the SeqCst settlement decrement, which
is a release RMW. An acquiring `in_flight` load observing the decremented
zero synchronizes with that release and publishes the earlier tally update
before the observer reads its report. The observer may see nonzero and wait
again; it must not see zero with a stale finished tally. The tally's Relaxed
accesses create no independent publication edge. Final joins order both
threads before the final zero/tally assertions.

For kind-limited demands, production claim checks kind counters and claims
packed total/permit state under the kind lock. Production release subtracts
kind counters and packed state within that same kind-lock critical section.
Mutex unlock to a subsequent lock provides the counter and resource
publication edge and prevents two releases overwriting a subtraction.
Packed release uses a Release decrement; successful claim uses an Acquire
CAS reading that decrement or its release sequence, which also publishes
the previous holder's work. The packed seed/failure Relaxed operations do
not provide publication. The fixture's Relaxed resource store/load
deliberately supplies no independent edge. Loom Arc ownership and joins
provide lifetime and post-thread observation ordering, not ordering between
the two concurrent releases.

The `oa-11-kind-release` alternative takes a kind-counter snapshot under
the lock, updates the snapshot after unlocking, returns packed capacity,
then writes the snapshot under a later lock. Two releasers can both read
the original counters and later overwrite one another's result. The
parallel-return fixture checks balanced packed state first, then exact zero
kind counters and full reacquisition. The separate publication fixture has
only one previous holder, so it remains the expected positive companion.
