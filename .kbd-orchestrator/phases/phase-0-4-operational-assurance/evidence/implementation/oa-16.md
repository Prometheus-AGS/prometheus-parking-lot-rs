## Deterministic failure schedule

The fixture starts a new owned container of
`apache/iggy:0.9.0@sha256:b35fc2841964f2962a5f164d33b3ae3a9de99a66920defd3cd8a1c039470602d`.
It sets `IGGY_MESSAGE_BUS_MAX_MESSAGE_SIZE=16 KiB` only for that container.
Stream names contain the process ID and current timestamp; topic names contain
the timestamp. One partition makes read ordering explicit. No shared or
production stream, topic, volume, or server is used.

1. Publish and flush `job-hole` sequences 1 and 2; require two successful
   publications and no abandoned message.
2. On the current-thread runtime, enqueue sequence 3 with a 64 KiB string,
   valid sequences 4 and 5, and a separate healthy writer's chunk and completed
   end marker. The empty bounded queue has eight slots. Before allowing the
   worker to run, require seven total accepted envelopes and unchanged
   published/failed counters. This asserts that later chunks were already
   queued before sequence 3 could be abandoned.
3. Flush the worker with a 30-second bound. Each publish attempt has a
   five-second timeout. The retry policy allows three attempts with 100 ms
   backoffs. The server's wire decoder rejects sequence 3 before reading its
   oversized body on each attempt. A paused server is not used: an ambiguous
   timed-out request must not arrive after the fixture resumes the server.
4. Read `job-hole` through the real `IggyStreamReader`, require chunks 1 and 2
   with their original data, then require the next call to remain pending for
   two seconds. This is the first poisoning oracle, named
   `OA-16:no-publication-past-hole`.
5. Require `writer.is_poisoned()`, `send` and `finish` returning
   `StreamError::Poisoned`, unchanged next sequence and enqueue count, three
   failed envelopes (abandoned 3 plus suppressed 4 and 5), exactly two added
   retries, four successful publications including the healthy writer, and no
   dropped envelope.
6. Strictly poll the real topic and require the distinct `job-hole` sequences
   to be exactly 1 and 2. Poll errors propagate instead of being treated as an
   empty topic. Consumer deduplication remains required; this does not solve
   excluded issue #62.
7. Reconnect with a new reader. Resume the valid prefix both with its real
   offset hint and by sequence alone; require each next call to wait. Read the
   healthy writer's chunk and completed end marker to establish that the
   publisher/server remain usable after the selected rejection.

The two-second waits are finite absence observations. The stronger supporting
conditions are that the publisher was drained, later envelopes were already
queued, a healthy writer continued on the same publisher, and a strict real-log
read found no tail. The fixture does not claim to prove behavior for every
possible future network schedule.

## Source basis for the fault boundary

Read-only source retrieval during task 1 established the configuration and
payload assumptions below. No server was launched to confirm them.

- Apache Iggy tag `server-0.9.0`,
  [message-bus configuration](https://github.com/apache/iggy/blob/server-0.9.0/core/configs/src/server_config/message_bus.rs):
  `max_message_size` is the wire-frame ceiling.
- The same tag's
  [server configuration](https://github.com/apache/iggy/blob/server-0.9.0/core/configs/src/server_config/server.rs)
  derives the `IGGY_` environment mapping and includes the `IGGY_MESSAGE_BUS_`
  section. The fixture uses `IGGY_MESSAGE_BUS_MAX_MESSAGE_SIZE`.
- The same tag's
  [frame decoder](https://github.com/apache/iggy/blob/server-0.9.0/core/message_bus/src/framing.rs)
  checks the reported frame size against the configured ceiling before reading
  its body; an oversized frame returns `InvalidCommand`.
- The official pinned
  [iggy_common 0.11.0 crate source archive](https://static.crates.io/crates/iggy_common/iggy_common-0.11.0.crate),
  `src/types/message/iggy_message.rs`, defines a 64,000,000-byte payload maximum.
  The chosen 64 KiB chunk is below that client-side limit and above the test
  server's 16 KiB wire-frame limit.

The final gate must confirm that the pinned image actually accepts the override
and exhibits this rejection with the pinned SDK. Source inspection is not
substitute evidence for that runtime behavior.

Run only through oa-18 task 2 after the whole planned implementation set is
complete, on a quiet machine, with serialized Cargo commands and the frozen


Negative control, evaluated separately from the normal build:

```bash
RUSTFLAGS='--cfg parking_lot_negative_control="oa-16"' cargo nextest run -p prometheus-parking-lot-iggy --all-features --locked --run-ignored all --no-tests=fail -E 'test(iggy_stream_abandoned_chunk_poisons_writer_and_preserves_prefix)'
```

This control must compile and discover the named test, then fail specifically at
`OA-16:no-publication-past-hole` with
`Gap { expected: 3, got: 4 }`. It disables the poison store, so queued valid
sequences 4 and 5 remain publishable after the selected failure. The real
reader's gap is the distinguishing failure. A compiler error, no tests,
container startup failure, unrelated assertion, backend error, or outer test
timeout is not successful negative-control evidence. Do not combine this cfg
with the existing `s-33` control, which changes reader gap handling.

The final runner owns candidate SHA, resolved manifest/test discovery, source
and fixture digests, lockfile/toolchain and actual tool versions, OS/Docker and
image identities, exact argv, timestamps, exits, and raw redacted stdout/stderr
logs. Preserve both passing and failed receipts. The test emits stream/topic
identity and publisher counters. Its armed failure guard emits the owned
container's logs on scenario error or panic before testcontainers removes the
container. Startup login failure also emits logs. A failure before a container
handle exists cannot use that guard; preserve the testcontainers diagnostic.

Keep `RUSTFLAGS` settings separate in the driver's normal/control execution
plan; do not alternate them in an implementation check loop. No extra target
directory, tool installation, Docker prune, host tuning, or account operation is
